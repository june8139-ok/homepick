## 1. Vision

### 1.1 제품 비전

대한민국 부동산 의사결정 플랫폼은 아파트 분양·계약 과정에서 발생하는 정보 비대칭을 줄이고, 사용자가 **데이터와 실제 경험**을 바탕으로 더 나은 선택을 할 수 있도록 돕는 서비스이다.

> *누군가의 가장 큰 선택이, 가장 좋은 선택이 되도록.*

### 1.2 핵심 가치

- **투명성**: 계약조건, 분양정보, 후기를 한곳에서 확인
- **비교 가능성**: AI 기반 단지 비교·추천으로 객관적 판단 지원
- **신뢰성**: Verified Buyer 인증 후기 등 실제 계약자 경험 반영
- **접근성**: Smart Search·자동완성으로 누구나 쉽게 탐색
- **개인화**: 관심 단지·가격 변동 알림으로 적시에 정보 제공
- **발견성**: SEO 최적화 상세 페이지·연관 단지 제안으로 유입·탐색 강화

### 1.3 타겟 사용자

| 구분 | 설명 |
|------|------|
| 1차 타겟 | 아파트 분양·청약을 검토 중인 예비 구매자 |
| 2차 타겟 | 기존 단지와 비교하려는 이사·갈아타기 검토자 |
| 3차 타겟 | (향후) 중개·컨설팅 등 부동산 관련 전문가 |

## 3. Smart Search

### 3.1 목적

사용자가 **단지명**을 빠르고 정확하게 입력·선택하여 검색 결과 페이지로 이동할 수 있게 한다.

### 3.2 검색 입력

| 항목 | 내용 |
|------|------|
| Placeholder | 단지명을 입력하세요 |
| 입력 방식 | 텍스트 직접 입력 |
| 최소 입력 길이 | 추후 정의 |
| 특수문자·공백 처리 | 추후 정의 |

### 3.3 Smart Search with Autocomplete

입력과 동시에 **단지·지역·브랜드** 후보를 제안하는 자동완성을 Smart Search의 핵심 기능으로 포함한다.

| 항목 | 요구사항 |
|------|----------|
| 트리거 | 사용자 입력 **1자 이상** 시 debounce(약 200~300ms) 후 제안 목록 표시 |
| 제안 소스 | 등록 단지명, 공식 약칭, 브랜드(예: ○○자이), 시·구·동 지역명 |
| 표시 형식 | 단지명 + 소재지(구/동) + (선택) 분양 상태 태그 |
| 하이라이트 | 입력어와 일치하는 부분 강조 |
| 키보드 | ↑↓ 이동, Enter 선택, Esc 닫기 |
| 모바일 | 터치 선택 시 즉시 검색 또는 상세 이동 |

**제안 우선순위 (초안)**

1. 단지명 prefix·부분 일치
2. 오타·유사어 보정 (예: 「래미안」↔「레미안」)
3. 지역명 + 인기 단지
4. (로그인 시) 최근 검색·관심 단지

**부가 UI**

- 검색창 포커스 시: **인기 검색어**·**최근 검색어**(로컬/계정) 노출
- 제안 0건: 「○○와(과) 유사한 단지」 안내 → §4.6 연관 제안과 연동

### 3.4 검색 트리거

- Enter 키 입력
- (선택) 검색 버튼 클릭
- (선택) 자동완성 항목 선택

### 3.5 검색 실패·예외 처리

- 결과 없음
- 오타·유사 단지 제안
- 네트워크 오류

| 분양·계약 정보 | 분양가, 계약조건, 옵션, 변경 이력 | P0 |

- 변경 이력 조회 (추후 범위 정의)

- 비로그인 시 로그인 유도 후 찜 가능

### 5.5 SEO Optimized Apartment Pages

각 단지 상세 URL은 **검색 엔진·SNS 공유**에 최적화되어 organic 유입을 극대화한다.

| 항목 | 요구사항 |
|------|----------|
| URL 구조 | 의미 있는 slug (예: `/apartments/판교-○○자이`) — ID-only URL 지양 |
| Title | `{단지명} 분양정보 \| {구/시} 아파트 \| {서비스명}` |
| Meta description | 단지 핵심 정보(위치, 분양 상태, 가격대) 120~160자 자동·수동 생성 |
| Open Graph | og:title, og:description, og:image(대표 단지 이미지) |
| Structured data | JSON-LD `RealEstateListing` 또는 `ApartmentComplex` (스키마 검증) |
| Canonical | 중복 URL 방지 canonical 태그 |
| Heading | h1=단지명, h2=섹션(분양정보, 위치, 후기 등) 계층 준수 |
| 성능 | LCP·CLS 등 Core Web Vitals — 이미지 lazy load, next/image 활용 |
| Admin | Site Settings·Admin(§14)에서 SEO 필드 편집·미리보기 |

## 9. Verified Buyer Reviews

### 9.1 목적

후기의 **신뢰도**를 높이기 위해, 해당 아파트에 **실제로 계약한 사용자만** 계약 사실을 증명하고 **Verified Buyer(인증 계약자)** 뱃지를 부여하는 시스템이다.

인증을 통과한 사용자의 후기에만 뱃지가 표시되며, 미인증 사용자는 뱃지를 받을 수 없다.

### 9.2 대상

| 구분 | 설명 |
|------|------|
| 인증 가능 | 해당 단지에 **실제 계약을 완료**한 사용자 |
| 인증 불가 | 방문만 한 사용자, 계약 전 사용자, 타 단지 계약자 |
| 뱃지 부여 | **인증 승인을 받은 경우에만** Verified Buyer 뱃지 부여 |

### 9.3 Buyer Verification Process (구매자 인증 프로세스)

실제 계약자만 Verified Buyer가 되도록 **신청 → 제출 → 심사 → 결과** 단계를 명확히 한다.

| 단계 | 주체 | 설명 |
|------|------|------|
| 1. 신청 | 사용자 | 후기 작성 전/후 또는 마이페이지에서 「계약 인증」 시작, **대상 단지** 선택 |
| 2. 자료 제출 | 사용자 | §9.4 인증 자료 1종 이상 업로드 또는 입력 |
| 3. 1차 검증 | 시스템 | 필수 필드·파일 형식·민감정보 마스킹 여부 자동 점검 |
| 4. 2차 심사 | Admin | §14 Admin Approval Workflow — 운영자 승인/거절/보류 |
| 5. (선택) AI 보조 | 시스템 | OCR·단지명 매칭 제안 → **최종 결정은 Admin** |
| 6. 결과 통지 | 시스템 | 승인 시 뱃지 부여·앱/이메일 알림; 거절 시 사유·재제출 안내 |
| 7. 후기 연동 | 사용자 | 승인 후 해당 단지 **계약 후기** 작성·수정 시 뱃지 자동 표시 |

**상태값 (초안)**

`draft` → `submitted` → `under_review` → `approved` | `rejected` | `pending_info`

**재제출**

- 거절 사유가 「자료 불충분」인 경우 **pending_info** 후 재업로드 가능
- 위조·타인 계약 등 중대 사유는 재제출 제한 — 추후 정책 정의

### 9.3.1 인증 플로우 요약 (사용자 관점)

1. 사용자가 후기 작성 또는 마이페이지에서 「계약 인증」 신청
2. 아래 **인증 자료** 중 하나 이상 제출
3. Admin 승인 워크플로(§14)를 통해 계약 사실 확인
4. 승인 시 해당 단지에 대해 **Verified Buyer** 뱃지 부여
5. 이후 작성·수정하는 해당 단지 후기에 뱃지 노출

### 9.4 인증 자료 (Verification Examples)

| 자료 유형 | 설명 | 비고 |
|-----------|------|------|
| Contract first page | 분양·매매 **계약서 1면**(당사자·단지·동·호 등 식별 정보 포함) | 민감 정보 마스킹 정책 적용 |
| Confirmation message | 분양사·시행사·중개 등에서 발송한 **계약 확정·안내 문자·알림톡** | 발신처·단지명·일자 확인 |
| Contract information | 계약번호, 계약일, 단지명, 동·호, 계약금 납부 내역 등 **계약 정보** | 위 자료와 교차 검증 |

- 제출 자료는 **해당 단지 계약과 일치**해야 하며, 위 항목만으로 판단이 어려운 경우 추가 자료 요청 가능
- 주민등록번호·계좌번호 전체 등 **불필요한 개인정보**는 수집·보관하지 않음 (추후 마스킹·보관 기간 정의)

### 9.5 Verified Buyer 뱃지

| 항목 | 내용 |
|------|------|
| 표시 위치 | 인증된 사용자의 후기 카드·프로필(닉네임 옆) |
| 표시 조건 | **인증 승인 완료** 후에만 표시 — 인증 없이는 뱃지 미부여 |
| 단지 단위 | 사용자·단지별로 인증 (A 단지 인증 ≠ B 단지 자동 인증) |
| 유효 기간 | 추후 정의 (계약 취소·해지 시 뱃지 회수 정책 포함) |

### 9.6 검증·거절

- 승인: 제출 자료와 플랫폼 단지·계약 정보 일치 시
- 거절: 자료 불충분, 타인 계약, 위조·편집 의심, 단지 불일치
- 거절 시 사유 안내 및 재제출 가능 여부 — 추후 정의

### 9.7 User Reviews(§8)와의 관계

- §8의 **계약 후기**는 Verified Buyer 인증과 연동하는 것을 권장
- 방문 후기 등 비계약 후기는 Verified Buyer 뱃지 **대상 아님** (별도 「방문 인증」은 향후 검토)
- 후기 목록·정렬에서 「인증 계약자 후기만 보기」 필터 — 추후 정의

### 9.8 Verified Buyer 후기 UX

| 요소 | 설명 |
|------|------|
| 후기 목록 | Verified Buyer 뱃지 아이콘 + 「인증 계약자」 라벨 |
| 필터 | 「인증 계약자 후기만 보기」 토글 (P1) |
| 정렬 | 「인증 후기 우선」 옵션 — 추후 A/B |

| 미인증 후기 | 작성 가능하나 **뱃지 미표시** — 인증 유도 CTA 노출 |

## 11. Favorite Apartments (관심 단지)

### 11.1 목적

사용자가 검토 중인 단지를 **저장(찜)**하고, 마이페이지에서 한곳에 모아 비교·알림(§12)의 기준으로 활용한다.

### 11.2 기능

| 기능 | 설명 | 우선순위 |

## 12. Price Change Notifications (가격·조건 변경 알림)

### 12.1 목적

### 12.2 알림 트리거

| 이벤트 | 설명 |
|--------|------|

### 12.3 기능

| 기능 | 설명 |
|------|------|
| 구독 설정 | 단지별·관심 단지 일괄 ON/OFF |

| 알림 빈도 | 즉시 / 일 1회 digest — 사용자 선택 |
| 알림 본문 | 변경 전·후 요약, 변경 일시, 상세 페이지 링크 |

2. 변경 diff 생성 → 알림 큐 적재

4. 사용자 클릭 → 단지 상세 **변경 이력** 섹션으로 앵커 이동

## 13. AI Recommendation Engine (AI 추천)

### 13.1 목적

사용자의 **검색·찜·조회 이력**과 단지 속성을 바탕으로, §6 AI Comparison(사용자 주도 비교)과 달리 **시스템이 선제적으로** 적합 단지를 추천한다.

### 13.2 §6 AI Comparison와의 차이

| 구분 | AI Comparison (§6) | AI Recommendation (§13) |
|------|-------------------|---------------------------|
| 주도 | 사용자가 단지 선택 | 시스템이 후보 제안 |
| 출력 | 2+N개 **비교표·요약** | ranked **추천 목록 + 이유** |
| 노출 | 비교 전용 화면 | 홈, 검색 결과, 상세 하단(§4.6, §5.6) |

### 13.3 입력 신호 (초안)

- 현재 검색어·필터
- 조회·찜한 단지
- (선택) 예산·평형·지역 선호 — 온보딩 또는 마이페이지
- Verified Buyer 후기 sentiment 요약

### 13.4 출력

| 항목 | 설명 |
|------|------|
| 추천 카드 | 단지 4~8건, **추천 점수·한 줄 이유** |
| 설명 가능성 | 「같은 학군」「20% 낮은 분양가대」 등 규칙+LLM 혼합 |
| 면책 | 「참고용 AI 추천」 고지, §6과 동일 정책 |

### 13.5 Admin·운영

- AI Management(04_Admin.md §9)에서 추천 항목 가중치·프롬프트 관리
- 부적절 추천 신고 → 로그 검수

## 14. Admin Approval Workflow (관리자 승인 워크플로)

### 14.1 목적

사용자 제출 콘텐츠·인증·(선택) 단지 정보 변경이 **운영 승인 후**에만 공개·효력을 갖도록 하는 **내부 처리 흐름**을 정의한다. 상세 Admin 기능은 [04_Admin.md](04_Admin.md) 참조.

### 14.2 승인 대상

| 대상 | PRD 연관 | Admin 메뉴 |
|------|----------|------------|
| Verified Buyer 인증 | §9 Buyer Verification | Admin §5 |
| 후기 (선택) | §8 — 신규·신고 재검토 | Admin §6 |
| 계약조건 변경 | §5.3, §12 | Admin §3 |
| 단지 신규·대규모 수정 | §5 | Admin §2 |
| 광고 게재 | §7 (향후) | Admin §7 |

### 14.3 공통 워크플로

```
[사용자/Editor 제출] → [대기 큐] → [Operator 검토]
                              ↓
            ┌─────────────────┼─────────────────┐
         승인(approve)      보류(pending)      거절(reject)
            ↓                  ↓                  ↓
      서비스 반영      추가 자료 요청        사유 통지
      (알림 발송)      (재제출 대기)        (재제출 정책)
```

### 14.4 Verified Buyer 승인 (§9 연동)

1. `submitted` 건이 Dashboard·Admin §5 큐에 적재
2. Operator가 §9.4 자료와 DB 단지 정보 대조
3. **approve** → Verified Buyer 뱃지 + 사용자 알림
4. **reject** / **pending_info** → §9.3 상태 전이 및 사유 기록
5. 모든 조치 **audit log** (처리자, 일시, 코멘트)
